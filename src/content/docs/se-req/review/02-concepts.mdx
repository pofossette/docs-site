## 一、需求本质与分层体系

| 概念名称 | 核心定义与内涵 | 典型应用与工程作用 | 易混点与易错提示 |
| :--- | :--- | :--- | :--- |
| **软件需求 (Software Requirements)** | 用户对目标软件系统在功能、行为、性能、设计约束等方面的期望，包含求解现实问题的全部条件与权能 | 项目立项、系统设计、开发编码与验收测试的共同基础 | 需求是说明系统“做什么”，绝不是描述程序算法和内部结构“怎么做” |
| **业务需求 (Business Requirements)** | 反映组织机构或客户对系统、产品的高层次战略目标与商业利益要求 | 记录在《项目视图与范围文档》中，统领全局方向 | 抽象层级最高；只阐述为什么需要该软件，不展开具体功能点 |
| **用户需求 (User Requirements)** | 描述用户使用软件产品必须能够完成的具体业务任务与操作场景 | 记录在用例文档或用户故事中，指导用户交互设计 | 是用户的业务活动描述，而非系统内部的技术实现需求 |
| **功能需求 (Functional Requirements)** | 开发人员必须在系统中实现的软件功能，使最终用户能够顺利完成其任务 | 详细写入软件需求规格说明书 (SRS) 的第 3 章“系统特性”中 | 必须具备明确的输入、行为和预期输出，具备可测试性 |
| **非功能需求 (Non-functional Requirements)** | 系统必须具备的属性、环境要求、行为品质与约束（包含质量属性与设计约束） | 约束软件架构设计，保障系统高可靠、高可用、高安全性 | 绝非可有可无的次要项；非功能需求的失败往往直接导致整个项目报废 |
| **设计约束 (Design Constraints)** | 对系统架构选型、技术栈、编程语言、通信协议或运行硬件施加的限制条件 | 保证与遗留系统的兼容性、满足企业IT规范或合规要求 | 是对方案空间的限制，而非用户业务功能的直接扩充 |
| **项目视图 (Project Vision)** | 项目的战略定位与长远蓝图，勾画产品在理想环境中的最终形态 | 统一所有利益相关者的长远预期，防止团队迷失方向 | 视图具有长远性和前瞻性；不可将当前版本的现实边界与长期视图混淆 |
| **项目范围 (Project Scope)** | 明确当前软件版本具体应该包含和绝对不包含的内容、功能和边界 | 界定开发团队的工作责任界限，防范无节制的需求膨胀 | 必须同时划定“做什么”和“明确不做什么（Out of Scope）” |
| **业务规则 (Business Rules)** | 关于业务操作、原则或政策的陈述，独立于软件系统存在，界定企业运行准则 | 作为派生功能需求的来源（如：满减规则、审批权限层级等） | 业务规则不是软件需求本身；但业务规则决定了系统需要哪些功能 |

## 二、客户利益、角色与分析员能力

| 概念名称 | 核心定义与内涵 | 典型应用与工程作用 | 易混点与易错提示 |
| :--- | :--- | :--- | :--- |
| **客户 (Customer)** | 为软件产品买单、享有投资回报或直接/间接从软件成果中获益的个人或组织 | 决定项目资金投入、验收产品成果并提出核心业务需求 | 客户包括最终用户，但掏钱买软件的客户并不一定是系统的直接操作者 |
| **最终用户 (End User)** | 每天在终端实际操作软件、使用各项具体功能完成日常业务的人员 | 参与需求获取访谈、提供界面可用性反馈与实机验收 | 最终用户的诉求侧重于好用、省力，可能与出资客户的成本管控产生冲突 |
| **产品倡导者 (Product Champion)** | 来自特定用户类的骨干代表，作为需求分析员与该类用户沟通的主接口人 | 收集并归纳本用户类的共性需求，仲裁本类内部的细微冲突 | 是用户方的代言人，必须具备深厚业务经验并被本部门充分授权 |
| **客户权利 (Customer Rights)** | 客户在需求工程全周期中应享受的 10 项核心权利（如要求用用户语言交流等） | 维护客户的核心利益，建立平等、互信的甲乙合作关系 | 客户有权要求评估成本和可行性，但评估的执行主体是分析员/开发团队 |
| **客户义务 (Customer Obligations)** | 客户在需求工程中必须承担的 10 项责任（如及时做出决策、详细描述需求） | 约束客户积极参与，防范“需求空降”与“拖延决断” | 需求确认是客户的法定义务；不能指望只提粗略设想就由开发方全盘包办 |
| **需求分析员 (Requirements Analyst)** | 负责沟通客户并把现实业务问题转换为严谨工程需求的“软件系统翻译官” | 组织需求获取、建立系统模型、编制 SRS、协调技术与业务冲突 | 核心职责是“发现并定义真实需求”，而不是直接编写业务代码 |

## 三、需求工程全周期与过程模型

| 概念名称 | 核心定义与内涵 | 典型应用与工程作用 | 易混点与易错提示 |
| :--- | :--- | :--- | :--- |
| **需求工程 (Requirements Engineering)** | 覆盖需求开发与需求管理全生命周期、用于建立并维护系统需求的系统工程学 | 确保软件开发不仅把事情做对（Do things right），更把对的事情做出来 | 需求工程不是瀑布模型的专利；敏捷迭代与演化开发同样高度依赖需求工程 |
| **需求开发 (Requirements Development)** | 包含获取、分析、编写规格说明和验证 4 个主要阶段的工程技术活动群 | 产出项目范围说明书、用例模型、系统关联图与正式 SRS 制品 | 侧重于“创造、提炼与验证”需求内容本身 |
| **需求管理 (Requirements Management)** | 包含版本控制、变更控制、状态跟踪与需求跟踪 4 大支撑机制的管理活动群 | 在开发进行过程中确保需求受控演进，维护制品与代码的一致性 | 侧重于“控制、度量、跟踪与变更治理”，贯穿项目始终 |
| **需求基线 (Requirements Baseline)** | 经过正式评审并由双方签字承诺、在某一特定版本中实现的受审需求集合 | 作为后续系统设计、编码实现、测试用例编写与进度考核的基准 | 基线不意味着不可变；而是意味着“任何变动必须经过严格的受控变更流程” |
| **需求属性 (Requirement Attributes)** | 为每条需求附加的一组标准化元数据（如唯一编号、状态、版本号、作者、优先级、实现成本等） | 支撑细粒度的需求状态跟踪、变更管理与度量分析 | 需求不仅仅是一句话；没有属性的需求无法在工程中进行受控管理 |
| **范围蔓延 (Scope Creep)** | 在项目进行过程中，未经正规 CCB 评审批准而擅自、渐进式追加新特性的恶性工程现象 | 软件项目延期超支的首要元凶；破坏既定进度与质量基线 | 拒绝范围蔓延不等于拒绝变更；合法变更需走正规 CCB 审批流程 |

## 四、需求分析与系统建模技术

| 概念名称 | 核心定义与内涵 | 典型应用与作用 | 易混点与易错提示 |
| :--- | :--- | :--- | :--- |
| **关联图 (Context Diagram)** | 将整个目标系统视为单个顶层加工，只显示系统与外部实体之间交互的顶层图 | 明确界定系统与现实世界/外部环境的边界与数据流接口 | 关联图内部绝不拆分子处理过程；系统本身就是一个单一圆角矩形/椭圆 |
| **数据流图 (DFD)** | 描绘数据在系统中流动、存储和被加工处理变换过程的图形工具 | 结构化分析的核心工具，展现功能过程与数据传递路径 | 严禁黑洞（只有入流无出流）、奇迹（无入流只有出流）和灰洞错误 |
| **外部实体 (External Entity)** | 存在于目标系统边界之外，向系统提供数据或接收系统输出的人员、组织或外部硬件 | DFD 和关联图的重要元素，用矩形框表示 | 外部实体必须在系统边界外；系统内部的模块或数据库绝不是外部实体 |
| **数据存储 (Data Store)** | 系统内部保存数据的逻辑集合（如数据库表、文件、缓存），用开口矩形表示 | 存储加工的中间或最终结果，供后续加工读取 | 数据不能直接在两个数据存储之间流动，必须经由加工（Process）处理 |
| **数据字典 (Data Dictionary, DD)** | 对系统使用和流动的所有数据元素、数据流、数据存储进行严格定义的权威仓库 | 消除需求多义性，为数据库设计与接口定义提供统一语义标准 | DFD 展现结构，DD 展现细节；没有数据字典的 DFD 是不严密的 |
| **用例图 (Use Case Diagram)** | 面向对象需求分析工具，描述行为者（Actor）与系统所提供的服务（Use Case）间的交互 | 快速捕获用户操作目标，作为编写用例文档与系统测试的纲领 | 用例颗粒度需合理；不要把细碎的按钮点击误当成独立用例 |
| **活动图 (Activity Diagram)** | 描述由用例引发的业务操作顺序、分支判定与并发执行逻辑的流程图 | 展现跨对象、跨职责（泳道）的业务流转与算法步骤 | 侧重于系统动作（Actions）的推进，而不是对象状态的停留 |
| **时序图 (Sequence Diagram)** | 沿时间轴向下展现多个对象之间交换的消息调用序列的交互图 | 精确描述复杂业务场景下对象间的调用时序与协作机制 | 垂直虚线为对象生命线，水平箭头表示调用消息，注重时间次序 |
| **决策表 (Decision Table)** | 用行列矩阵穷尽表达复杂多条件组合判断及对应执行动作的表格工具 | 处理高复杂度的业务规则（如阶梯电价、行李费率、审批策略） | 必须检查规则完整性与相容性；规则总数为 $2^n$（$n$ 为独立二值条件数） |
| **决策树 (Decision Tree)** | 以树根到叶子结点的分层分支，直观展示条件判断逻辑顺序与动作的树形工具 | 向非技术业务人员展示判定逻辑，直观形象易于推演 | 当条件极多且交叉时容易产生大量重复分支；此时决策表更紧凑 |
| **状态转换图 (State Transition Diagram, STD)** | 描绘系统、实体或用例在其生命周期内经历的所有状态、引发转换的事件及执行动作的模型 | 针对具有丰富状态变化的控制系统或复杂生命周期的订单/工单流程 | 状态表示实体停留的状况；事件是触发转换的触发器；动作是伴随转换执行的操作 |

## 五、需求文档编制与质量属性

| 概念名称 | 核心定义与内涵 | 典型应用与工程作用 | 易混点与易错提示 |
| :--- | :--- | :--- | :--- |
| **SRS (Software Requirements Spec)** | 软件需求规格说明，是全面描述目标系统功能、性能与设计约束的正式工程文档 | 软件团队唯一的“施工图纸”，是验收交付的技术与法律合同 | 必须使用精准无歧义的陈述；避免出现“大约”、“极快”、“等等”等模糊词 |
| **TBD (To Be Determined)** | 在需求规格说明编写中，对暂时由于外部条件不具备而尚未决定的内容所作的显式标记 | 承认不完整性并集中管理未知风险，防止将“不知道”伪装成“完整” | 严禁滥用 TBD；每个 TBD 必须指定责任人、解决期限与决策依据 |
| **可用性 (Availability)** | 系统按要求处于正常工作状态并能被用户随时访问调用的时间百分比 | 常见衡量标准：99.9%（千分之一停机）、99.99% 等高可用指标 | 与“可靠性”不同：即使系统偶发故障，但能秒级故障转移自动重启，可用性依然极高 |
| **可靠性 (Reliability)** | 系统在规定的工作环境和给定的时间段内，维持无故障平稳运行的概率 | 关键指标：平均无故障工作时间 (MTBF)、平均修复时间 (MTTR) | 可靠性注重“不出故障的持续能力”；可用性注重“用户随时能用到的概率” |
| **可维护性 (Maintainability)** | 发现系统缺陷、诊断根因、修改代码并完成回归测试的便捷程度 | 决定软件长达数年运维期的总拥有成本 (TCO) | 主要属于开发人员关心的质量属性，通常与系统的架构解耦度高度正相关 |
| **质量属性折中 (Trade-off)** | 针对相互冲突的质量属性，权衡业务收益与研发成本达成最优平衡的技术方案 | 架构设计决策；如为了极致的安全性引入双因子验证，牺牲了部分易用性 | 质量属性不可能全部达到最高；无原则的盲目承诺会导致灾难性架构冲突 |
| **易用性 (Usability)** | 衡量最终用户掌握系统操作的容易程度、任务执行效率以及使用满意度的品质特征 | 影响用户接受度、培训成本与日常业务出错率 | 易用性属于外部质量属性；不是简单的“界面好看”，而是操作顺手、反馈即时 |

## 六、原型技术与优先级量化

| 概念名称 | 核心定义与内涵 | 典型应用与工程作用 | 易混点与易错提示 |
| :--- | :--- | :--- | :--- |
| **抛弃式原型 (Throwaway)** | 仅用于探明模糊需求或界面交互，验证完毕后将其代码完全弃置的原型 | 需求获取阶段探索用户真实习惯；风险排除后重新按正规架构编码 | 绝不能为了赶工将粗制滥造的抛弃式原型直接修补上线运行 |
| **演化式原型 (Evolutionary)** | 从设计之初就具备规范架构与高质量代码，后续版本在其基础上增量扩展的原型 | 敏捷开发、持续交付与快速推向市场的 MVP 战略 | 演化式原型的第一行代码就必须满足生产级编码规范与架构设计要求 |
| **水平原型 (Horizontal)** | 提供广泛的用户界面导航与展示，但不打通底层数据库与后台业务逻辑（门面系统） | 评估人机交互体验、确认界面布局、梳理用例工作流 | 用户在水平原型上看到的数据往往是写死的 Mock 数据，不能执行真实运算 |
| **垂直原型 (Vertical)** | 挑选少数关键核心功能，向下垂直打通从前端、中台到底层数据库和网络的完整链路 | 概念验证 (PoC)、探索技术瓶颈、验证复杂核心算法的性能 | 功能覆盖面窄，但技术下潜极深，专攻底层关键技术风险 |
| **Wiegers 优先级模型** | 结合价值（收益×2+损失×1）、成本（权重1）与风险（权重0.5）的量化计算法 | 消除用户“全要最高优先级”的盲目冲动，客观推导研发排期 | 计算过程先算各单项百分比，再代入综合公式计算最终优先级指数 |

## 七、确认评审、变更治理与需求跟踪

| 概念名称 | 核心定义与内涵 | 典型应用与工程作用 | 易混点与易错提示 |
| :--- | :--- | :--- | :--- |
| **需求确认 (Validation)** | 评估需求文档是否正确描述了用户真实需要，回答“是否在构建正确的系统” | 由用户代表深度参与，审查用例与需求是否对齐商业目标 | 容易与“验证”混淆；确认针对用户真实意图，验证针对工程规范一致性 |
| **需求验证 (Verification)** | 检查需求文档编写是否规范、逻辑是否严密，回答“是否在正确地构建需求” | 语法审查、形式化核对、是否符合 IEEE 830 标准规范 | 验证强调“合规与严密”；确认强调“对准用户真实需求” |
| **正式审查 (Formal Inspection)** | 最严密的同行评审形式，包含规划、准备、会议、返工等 6 阶段规范纪律 | 软件工程公认发现缺陷率最高、经济效益最好的质检工具 | 审查会议的目标是“发现并记录缺陷”，严禁在会上当场讨论如何修改代码 |
| **CCB (变更控制委员会)** | 由项目经理、客户代表、分析员、开发负责人与测试组长组成的权威决策机构 | 评估变更影响，审定每个需求变更请求（批准、推迟、拒绝） | 任何个人无权擅自答应客户变更需求；所有变更必须且只能由 CCB 批准 |
| **变更影响分析 (Impact Analysis)** | 评估实施某项变更对现有基线、软件架构、进度、开发成本及风险带来的波及面 | 填写 13 项核对清单，为 CCB 决策提供详实量化依据 | 不能仅估算编写该代码的工时，必须把回归测试、文档更新与延期风险全部计入 |
| **需求跟踪能力 (Traceability)** | 能够在软件制品的整个生命周期中，正向追溯并反向回溯某项需求的能力 | 变更波及面分析、证明系统无未实现功能、证明代码无镀金代码 | 维护跟踪矩阵需要高昂的工程成本；应优先在核心与关键安全需求上建立矩阵 |
| **RTM (需求跟踪矩阵)** | 交叉映射“用例 ↔ 功能需求 ↔ 设计类 ↔ 代码文件 ↔ 测试用例”的多维网格表格 | 快速检索某个需求由哪个文件实现，哪条测试用例负责检验 | 需求发生变更时，通过 RTM 能在数分钟内精确定位必须同步修改的下游制品 |
| **双向跟踪 (Bi-directional Traceability)** | 涵盖顺向追溯（从业务需求向下追溯至代码与测试）与逆向回溯（从代码/测试用例反查需求来源）的能力 | 确保需求百分之百被实现，消除无源“镀金代码”，评估变更波及面 | 建立双向跟踪需要工具链支撑，维护成本高，需在核心关键需求上强制落地 |
